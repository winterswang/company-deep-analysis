# Company Deep Analysis V8.0 设计方案

## 一、设计理念

### 1.1 核心问题

V7.0 存在的问题：
1. **单次执行过长** - 整个分析流程一次完成，上下文膨胀导致质量下降
2. **错误难定位** - 某个环节出问题，整个分析失败
3. **输出质量不可控** - 每个阶段的输出没有检验机制
4. **不可恢复** - 中断后需要从头开始

### 1.2 V8.0 解决方案

**多阶段执行 + 阶段检验 + 持久化中间结果**

```
┌─────────────────────────────────────────────────────────────┐
│                    V8.0 多阶段架构                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  阶段1: 数据收集 ──→ [检验] ──→ 保存结果                     │
│      ↓                                                      │
│  阶段2: 财务异常 ──→ [检验] ──→ 保存结果                     │
│      ↓                                                      │
│  阶段3: 经营分析 ──→ [检验] ──→ 保存结果                     │
│      ↓                                                      │
│  阶段4: 护城河识别 ──→ [检验] ──→ 保存结果                   │
│      ↓                                                      │
│  阶段5: 不可复制性 ──→ [检验] ──→ 保存结果                   │
│      ↓                                                      │
│  阶段6: 报告生成 ──→ 最终报告                                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 核心优势

| 优势 | 说明 |
|------|------|
| **Context 聚焦** | 每个阶段只关注一个任务，上下文精简 |
| **质量可控** | 每阶段有明确的输出格式和质量检验 |
| **可恢复** | 从任意阶段继续，无需重头开始 |
| **可调试** | 单独测试和优化每个阶段 |
| **可增量** | 新数据只更新相关阶段 |

## 二、阶段设计

### 阶段 1：数据收集与质量验证

**职责**：收集财务数据，验证数据质量

**输入**：
```json
{
  "company": "PDD Holdings",
  "ticker": "PDD",
  "market": "us"
}
```

**输出**：
```json
{
  "stage": "data_collection",
  "status": "success",
  "data": {
    "financial_data": {
      "ROE": 44.92,
      "毛利率": 60.92,
      "营收": 3938.36,
      "净利润": 1124.35,
      ...
    },
    "quality_report": {
      "total": 7,
      "trusted": 7,
      "avg_score": 7.0
    }
  },
  "next_action": "stage2"
}
```

**检验标准**：
- 至少获取 5 个核心财务指标
- 平均质量评分 >= 6.0
- 如果不达标，返回缺失数据清单

**命令**：
```bash
python run_v80.py --stage 1 --company "PDD Holdings" --ticker PDD --market us
```

---

### 阶段 2：财务异常分析

**职责**：检测财务异常，生成深度追问

**输入**：阶段1的财务数据

**输出**：
```json
{
  "stage": "financial_anomaly",
  "status": "success",
  "data": {
    "anomalies": [
      {
        "metric": "ROE",
        "value": "44.9%",
        "description": "ROE 44.9% 显著高于行业均值（约15%）",
        "severity": "高",
        "question": "为什么 ROE 这么高？是运营效率还是财务杠杆？"
      }
    ],
    "primary_question": "ROE 44.9% 显著高于行业均值，核心驱动因素是什么？"
  },
  "next_action": "stage3"
}
```

**检验标准**：
- 至少识别 1 个财务异常
- 每个异常有明确的追问
- 追问指向具体的经营层面

---

### 阶段 3：经营分析

**职责**：分析经营表现，获取行业对比

**输入**：阶段2的异常 + 财务数据

**输出**：
```json
{
  "stage": "business_analysis",
  "status": "success",
  "data": {
    "insights": [
      "销售费用率仅 7.3%，远低于京东/阿里的 20%+",
      "零库存轻履约模式，资产周转率行业第一"
    ],
    "evidence": [
      {"source": "Tavily", "content": "费用控制能力...", "quality": "P2"},
      ...
    ],
    "key_capability": "极致成本控制 + 高效供应链"
  },
  "next_action": "stage4"
}
```

**检验标准**：
- 至少 2 条经营洞察
- 每条洞察有证据支撑
- 识别出核心经营能力

---

### 阶段 4：护城河识别

**职责**：识别护城河类型，验证竞争优势

**输入**：阶段3的经营分析

**输出**：
```json
{
  "stage": "moat_identification",
  "status": "success",
  "data": {
    "moat_type": "成本优势",
    "confidence": 0.85,
    "evidence": [
      "单订单履约成本仅为行业均值的 35%",
      "库存周转天数 12.3 天（行业 47 天）"
    ],
    "verification_questions": [
      "低成本来自规模、资源、地理位置还是流程？",
      "竞争对手能否复制这个成本结构？"
    ]
  },
  "next_action": "stage5"
}
```

**检验标准**：
- 明确的护城河类型
- 置信度 >= 0.7
- 至少 2 条验证证据

---

### 阶段 5：不可复制性分析

**职责**：分析护城河的可持续性

**输入**：阶段4的护城河类型

**输出**：
```json
{
  "stage": "sustainability",
  "status": "success",
  "data": {
    "sustainability": "强",
    "reasons": [
      "C2M 供应链响应能力已内化为组织惯性",
      "微信生态早期红利构建的零获客成本社交分发机制",
      "327 万源头农产品基地直连数据"
    ],
    "risks": [
      "Temu 海外履约成本可能侵蚀利润",
      "竞争加剧导致费用率上升"
    ],
    "conclusion": "成本优势难以被竞争对手在短期内复制，可持续性较强"
  },
  "next_action": "stage6"
}
```

**检验标准**：
- 明确的可持续性评级
- 至少 2 条支撑理由
- 至少 1 个风险因素

---

### 阶段 6：报告生成

**职责**：整合所有阶段结果，生成最终报告

**输入**：所有前置阶段的结果

**输出**：完整的 Markdown 报告

**报告结构**：
```markdown
# {公司名} 投资分析报告

## 一句话结论

|------|------|----------|
| ROE | 44.9% | 行业均值 15% |
| ... | ... | ... |

## 护城河分析
**类型**: 成本优势
**可持续性**: 强
**核心原因**: ...

## 投资建议
基于以上分析，建议...
```

## 三、技术实现

### 3.1 文件结构

```
company-deep-analysis-v8/
├── core/
│   ├── stage1_collector.py      # 数据收集
│   ├── stage2_anomaly.py        # 财务异常
│   ├── stage3_business.py       # 经营分析
│   ├── stage4_moat.py           # 护城河识别
│   ├── stage5_sustainability.py # 不可复制性
│   └── stage6_report.py         # 报告生成
├── scripts/
│   ├── run_v80.py               # 主入口
│   └── run_stage.py             # 单阶段执行
├── state/                       # 中间状态存储
│   └── {company}_{timestamp}/
│       ├── stage1_result.json
│       ├── stage2_result.json
│       └── ...
├── reports/                     # 最终报告
└── config.yaml                  # 配置文件
```

### 3.2 执行方式

**方式 1：自动执行全部阶段**
```bash
python run_v80.py --company "PDD Holdings" --ticker PDD --market us
```

**方式 2：单阶段执行**
```bash
python run_v80.py --stage 1 --company "PDD Holdings" --ticker PDD
python run_v80.py --stage 2 --state ./state/PDD_20260314/
python run_v80.py --stage 3 --state ./state/PDD_20260314/
...
```

**方式 3：从指定阶段继续**
```bash
python run_v80.py --resume --state ./state/PDD_20260314/ --from-stage 3
```

### 3.3 状态持久化

每个阶段完成后，结果保存为 JSON：
```
state/PDD_20260314_130500/
├── stage1_result.json
├── stage2_result.json
├── stage3_result.json
├── stage4_result.json
├── stage5_result.json
└── final_report.md
```

## 四、与 V7.0 对比

| 方面 | V7.0 | V8.0 |
|------|------|------|
| 执行方式 | 单次执行全部 | 分阶段执行 |
| 上下文 | 膨胀到数万 token | 每阶段聚焦 |
| 错误处理 | 整体失败 | 单阶段失败可重试 |
| 输出检验 | 无 | 每阶段有检验标准 |
| 可恢复 | 不可恢复 | 从任意阶段继续 |
| 调试难度 | 高 | 低（单阶段调试） |
